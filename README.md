سوال یک: merge و rebase

هر دو دستور برای ادغام تغییرات دو شاخه استفاده می‌شن ولی رفتارشون فرق داره. git merge تاریخچه رو دست‌نخورده نگه می‌داره و یه کامیت جدید به اسم merge commit می‌سازه که دو والد داره. شکل تاریخچه غیرخطی می‌شه. این روش امنه و تاریخچه واقعی رو حفظ می‌کنه و مناسب برای ادغام روی شاخه اصلی مثل main هست. git rebase کامیت‌های شاخه فعلی رو برمی‌داره و دونه‌دونه روی شاخه مقصد دوباره اعمال می‌کنه. این کار تاریخچه رو کاملاً خطی و تمیز می‌کنه ولی هش کامیت‌ها عوض می‌شه یعنی تاریخچه بازنویسی می‌شه. مناسب برای وقتیه که می‌خوای شاخه شخصی خودت رو با تغییرات جدید main آپدیت کنی قبل از merge نهایی. بهتره برای شاخه‌های عمومی و مشترک از merge استفاده کنیم چون تاریخچه رو خراب نمی‌کنه و برای تمیز کردن شاخه شخصی قبل از push از rebase استفاده کنیم.




سوال دو: انتخاب بخشی از تغییرات (Hunk)

hunk به یک تکه پیوسته از تغییرات داخل یه فایل مییگن. وقتی git diff می‌زنیم Git تغییرات نزدیک به هم رو توی یه hunk نشون مییده. برای بررسی تعاملی و انتخاب بخشی از تغییرات از دستور <git add -p <filename استفاده می‌کنیم. Git هر hunk رو نشون مییده و می‌پرسه چییکار کنی. گزینه‌های مهم اینا هستن: y یعنی این hunk رو stage کن. n یعنی این hunk رو stage نکن. s یعنی این hunk رو به hunk‌های کوچیک‌تر بشکن برای وقتی که چند تغییر نزدیک هم هستن. q یعنی خروج. فایده این کار اینه که باعث مییشه کامیت‌های منسجم بسازیم. یعنی فقط رفع باگ رو stage کنی و کامیت کنی بعد feature جدید رو جدا کامیت کنی. اینطوری تاریخچه خواناتره و اگه بعدا بخواهیم یه کامیت رو برگردونیم راحت‌تره.




سوال سه: یافتن منشأ خطا با git bisect

git bisect از الگوریتم جست‌وجوی دودویی استفاده می‌کنه تا سریع بفهمه کدوم کامیت باعث ایجاد باگ شده. به جای اینکه همه کامیت‌ها رو یکی‌یکی چک کنیم وسط بازه رو چک می‌کنه و هر بار نصفش می‌کنه. مراحل به این ترتیبه: اول git bisect start می‌زنیم. بعد git bisect bad می‌زنیم تا کامیت فعلی که خرابه رو bad علامت بزنیم. بعد <git bisect good <commit-hash می‌زنیم تا یه کامیت قدیمی که مطمئنیم سالمه رو good علامت بزنیم. بعد Git می‌ره وسط و یه کامیت رو checkout می‌کنه. تستش می‌کنیم. اگه خراب بود git bisect bad می‌زنیم و اگه سالم بود git bisect good می‌زنیم. این کار رو تکرار می‌کنیم تا Git بگه فلان کامیت اولین کامیت خرابه. در آخر git bisect reset می‌زنیم تا برگردیم سر جای اولمون. مثال: نسخه v1.0 سالم بوده ولی main خرابه. با دستورات بالا شروع می‌کنم و بعد از چند مرحله Git دقیقا می‌گه کدوم کامیت باگ رو وارد کرده. چرا مفیده؟ چون خیلی سریعه. مثلا بین ۱۰۰۰ کامیت فقط حدود ۱۰ مرحله لازمه تا کامیت خراب پیدا بشه در حالی که چک دستی ساعت‌ها طول می‌کشید.




سوال چهار: بررسی تغییرات پیش از کامیت

بخش اول: دستورهای بررسی وضعیت. git status وضعیت کلی مخزن رو نشون می‌ده که کدوم فایل stage شده کدوم نشده کدوم untracked هست. git diff تغییراتی که هنوز stage نشدن یعنی working directory در مقابل staging area رو نشون می‌ده. git diff --staged تغییراتی که stage شدن و قراره توی کامیت بعدی برن یعنی staging area در مقابل آخرین کامیت رو نشون می‌ده. تفاوتشون اینه که git diff چیزایی رو نشون می‌ده که هنوز اضافه نکردی ولی git diff --staged دقیقاً چیزایی رو نشون می‌ده که قراره کامیت بشن.

بخش دوم: اگه الان یه کامیت معمولی بدون a- بزنی فقط تغییراتی که قبلا stage کرده بودی توی کامیت می‌رن. تغییرات دوم یعنی تغییراتی که بعد از stage کردن فایل دوباره اعمال کردی توی working directory باقی می‌مونن و stage نمی‌شن. پوشه tmp هم چون untracked هست اصلاً کامیت نمی‌شه. چون که Git فقط محتویات staging area رو کامیت می‌کنه. دستور git commit -a همه فایل‌های tracked رو خودکار stage می‌کنه ولی کامیت معمولی این کار رو نمی‌کنه.

بخش سوم: برای جلوگیری از اضافه شدن پوشه tmp یه فایل به اسم .gitignore توی ریشه مخزن میسازیم و داخلش مینویسیم tmp/. آیا برای فایل‌هایی که قبلا tracked شدن هم کافیه؟ نه. .gitignore فقط روی فایل‌های untracked اثر داره. اگه فایلی قبلا کامیت شده باشه Git همچنان تغییراتش رو دنبال می‌کنه. برای اینکه دیگه دنبالش نکنه باید اول از tracking خارجش کنیم با دستور <git rm --cached <file.




سوال پنج: رفع merge conflict در کار گروهی

بخش اول: چرا conflict رخ داده؟ چون من و هم‌تیمی‌ام از یه کامیت مشترک شروع کردیم و هر دو همون خط از فایل README.md رو تغییر دادیم. Git نمی‌تونه خودش تصمیم بگیره کدوم تغییر رو نگه داره پس merge رو متوقف می‌کنه و ازمون می‌خواد خودمون تصمیم بگیریم. آیا هر تغییری conflict می‌سازه؟ نه. اگه من خط ۱ رو عوض کنم و هم‌تیمی‌ام خط ۱۰ رو Git خودش هر دو رو با هم merge می‌کنه. conflict فقط وقتی پیش میاد که تغییرات روی هم بیفتن یا خیلی نزدیک باشن و Git نتونه مطمئن بشه.

بخش دوم: شناسایی فایل‌های دارای conflict با دستور git status انجام می‌شه. فایل‌های conflicted زیر عنوان Unmerged paths مثل both modified: README.md نشون داده می‌شن. نقش conflict markers توی فایل اینه که وقتی فایل رو باز می‌کنیم این نشانه‌ها رو می‌بینیم. <<<<<<< HEAD شروع نسخه شاخه فعلی من. ======= جداکننده بین دو نسخه. >>>>>>> feature-description پایان نسخه شاخه ورودی. برای رفع conflict باید فایل رو دستی ویرایش کنیم چیزی که می‌خوایم رو نگه داریم همه marker ها رو پاک کنیم و ذخیره کنیم بعد git add README.md بزنیم و در نهایت git commit کنیم تا merge تموم بشه.

بخش سوم: اول فایل conflicted رو با یه ادیتور باز می‌کنیم. هر دو نسخه رو می‌بینم که با markerها جدا شدن. هر دو بخش رو نگه می‌دارم و فقط marker ها یعنی خطوط <<<<<<<، ======= و >>>>>>> رو پاک می‌کنم. طوری متن رو می‌نویسیم که هر دو تغییر به شکل منطقی و درست کنار هم قرار بگیرن. بعد فایل رو ذخیره می‌کینم.

بعدش باید تغییرات رو stage کنیم. برای این کار از دستور git add README.md استفاده می‌کنیم.

بعد از اینکه همه فایل‌های conflicted رو add کردیم، برای تکمیل merge یه کامیت می‌زنیم. دستور git commit رو می‌زنیم و Git یه پیام پیش‌فرض برای merge commit پیشنهاد مییده که می‌تونیم تاییدش کنیم یا عوضش کنیم.

برای اینکه مطمئن بشیم conflict markerها باقی نموندن، چند راه داریم. اول اینکه دوباره فایل رو باز می‌کنیم و با چشم چک می‌کنیم که هیچ <<<<<<< یا ======= یا >>>>>>> توش نمونده باشه. دوم اینکه از دستور git diff یا git diff --staged استفاده می‌کنیم و خروجی رو نگاه می‌کنیم که خطوط marker توش نباشه. سوم اینکه از دستور git grep -n "<<<<<<<" استفاده می‌کنیم که کل فایل‌های پروژه رو می‌گرده و اگه marker ای مونده باشه نشون می‌ده. اگه خروجی خالی بود یعنی همه چیز تمیزه.

بخش چهارم: برای لغو merge در حال انجام از دستور git merge --abort استفاده می‌کنیم. این دستور merge رو کاملا لغو می‌کنه، همه تغییرات مربوط به merge رو برمی‌گردونه و مخزن رو دقیقا به وضعیتی که قبل از شروع merge داشت برمی‌گردونه. یعنی هم فایل‌های conflicted به حالت قبل برمی‌گردن و هم هیچ کامیت merge‌ای ثبت نمی‌شه.




سوال ششم: انتخاب روش مناسب برای بازگرداندن تغییرات

بخش اول: برای این وضعیت از دستور git restore notes.txt استفاده می‌کنیم. این دستور تغییرات موجود در working tree را برای این فایل نادیده می‌گیرد و نسخه فایل را دقیقا به همان حالتی که در آخرین کامیت (یا در staging area) بوده برمی‌گرداند. چون تغییرات در staging area نیستند و با آخرین کامیت یکسان‌اند، با زدن این دستور فایل notes.txt به حالت قبلی خودش برمی‌گردد و بقیه فایل‌ها و کامیت‌ها هیچ آسیبی نمی‌بینند. این روش کاملا امن است، چون نه تاریخچه کامیت‌ها را تغییر میده و نه روی ناحیه staging اثر میگذاره. اگه بخواهیم مطمئن شیم که هیچ تغییر local دیگری هم باقی نمانده، می‌توانیم قبل از دستور اصلی با git status وضعیت را بررسی کنیم. همچنین جایگزین قدیمی این دستور git checkout -- notes.txt است، ولی در نسخه‌ های جدید Git استفاده از git restore توصیه می‌شود چون شفاف‌تر است و فقط برای بازگرداندن فایل‌ها به کار می‌رود.

بخش دوم: برای این کار از دستور git restore --staged notes.txt استفاده می‌کنیم. این دستور فایل را از ناحیۀ staging خارج می‌کند، اما نسخه ویرایش‌شده را در working tree دست‌نخورده نگه می‌دارد. یعنی تغییرات ما از بین نمی‌رود، فقط دیگر جزو تغییرات آمادۀ کامیت بعدی محسوب نمی‌شود. بعد از اجرای این دستور، اگر git status بزنیم، می‌بینیم که notes.txt زیر عنوان "Changes not staged for commit" قرار گرفته است. این دقیقاً همان حالتی است که می‌خواهیم: تغییرات در working tree هستند، ولی در staging نیستند. اگر بعداً دوباره بخواهیم این تغییرات را کامیت کنیم، کافی است دوباره با git add notes.txt آن‌ها را stage کنیم. روش جایگزین قدیمی این کار git reset HEAD notes.txt است، ولی استفاده از git restore --staged در نسخه‌های جدید Git خواناتر و مطمئن‌تر است، چون در git reset خطر اشتباه و پاک شدن تغییرات وجود دارد.

بخش سوم: روش مناسب در این موقعیت استفاده از دستور git revert است. برای این کار کافی است هش کامیت اشتباه را پیدا کنیم و دستور <git revert <commit-hash را بزنیم. این دستور یک کامیت جدید میسازه که دقیقا اثرات کامیت اشتباه را خنثی می‌کنه. یعنی اگه کامیت اشتباه یک خط اضافه کرده باشه، revert اون خط را حذف می‌کنه، و اگه خطی را حذف کرده باشد، آن را برمی‌گرداند. سپس این کامیت جدید را با git push به اشتراک می‌گذاریم.

دلیل اینکه حذف کامیت از تاریخچه و force push توی این موقعیت انتخاب مناسبی نیست اینه که اولا تاریخچه کامیت‌ها بازنویسی میشود و هش کامیت‌ها عوض میشود. همچنین چون هم‌تیمی‌ها اون کامیت رو دریافت کرده‌اند و روی آن ممکن است کار کرده باشند، اگر ما تاریخچه را بازنویسی کنیم و force push بزنیم، مخزن local هم‌تیمی‌ها با مخزن remote ناسازگار میشود و آن‌ها مجبور میشوند کارهای خود را دستی درست کنند. این کار باعث سردرگمی و از دست رفتن کار دیگران می‌شود. در مقابل، git revert تاریخچه را دست‌نخورده نگه می‌دارد، یک کامیت جدید و شفاف اضافه می‌کند که همه می‌توانند ببینند چه اتفاقی افتاده، و با هم‌تیمی‌ها هیچ مشکلی ایجاد نمی‌کند. به همین دلیل در شاخه‌های مشترک همیشه revert را به reset و force push ترجیح می‌دهیم.
